# 4 new features: verification gate, economy module, habit tracker, Bot Control redesign

## Context

After a large audit-and-fix pass on the dashboard + Discord bot, the user asked what's still missing and said they want new modules plus a redesign of the Bot Control Center dashboard page. They picked, via a multi-select: a virtual economy system (bot), anti-bot member verification (bot), a habit/goal tracker (dashboard), and confirmed they want the Bot Control redesign to cover all three axes — functional reorganization, visual refresh, and more real-time data. Two follow-up decisions were confirmed: the Security & Audit view stays inside Bot Control (not redirected to the existing `/discord/security/anti-raid` page), and the economy currency is named "Crédits ETHONE".

Exploration (3 parallel Explore agents + verification reads) found that verification is already half-built (just not wired as a join gate), and that several Bot Control tabs fetch real backend data but never render it, or the backend itself fakes the data (Performance tab). Implementation order below is smallest/highest-value first so the session can ship incrementally and stop at a clean point if needed.

## 1. Anti-bot verification join gate (do first — smallest, reuses existing code)

`discord-bot/src/modules/welcome/` already has `VerificationConfigSchema`, `VerificationService.verifyMember` (adds verified role, removes unverified role), and a dashboard `GET/PUT /verification` route (`server/routes/welcomeRoutes.ts` ~L91-106) — it's just never enforced as a join gate, and the PUT handler is missing the `emitConfigUpdated` call every other module's config route has.

- **`welcomeRoutes.ts`**: add `emitConfigUpdated('welcome', guildId, updated, 'DASHBOARD', req.user?.id)` to the PUT `/verification` handler, mirroring `antiRaidRoutes.ts`'s PUT `/config`.
- **`discord-bot/src/events/guildMemberAdd.ts`**: immediately before the existing `autoRoleService.assignOnJoin(member)` call (~L30), read `welcomeRepository.getVerificationConfig(member.guild.id)`. If `enabled`, assign `unverifiedRoleId` (if set) and skip `assignOnJoin` for this member; otherwise call `assignOnJoin` as today. Stay inside the file's existing single top-level try/catch — don't add a nested one.
- **`discord-bot/src/modules/welcome/services/verificationService.ts`**: inside `verifyMember`, after the existing role add/remove succeeds, call `autoRoleService.assignOnJoin(member)` so gated members get their normal auto-roles the moment they verify instead of never.
- **Optional, do last, keep minimal**: new `discord-bot/src/modules/welcome/commands/verificationCommand.ts`, a `/verification` command with only `status` and `toggle <actif:boolean>` subcommands (not a full config-editing surface — that stays dashboard-only, matching the channel/role/button-label fields). Register in `commandHandler.ts`.

`member.roles.add()` is idempotent at the Discord API level, so there's no real double-assignment risk — the risk is *forgetting* the `verifyMember` restore step, which would silently strand verified members without their normal roles.

## 2. Economy module ("Crédits ETHONE") — new bot module

Clone the `leveling` module's shape (`discord-bot/src/modules/leveling/{types,storage,services,commands}/`). Scope capped to: balance, `/daily` claim, `/pay` transfer, leaderboard, one gambling command (coinflip), and a shop limited to purchasable Discord roles. No inventory system, no bank/interest, no crafting.

- **Types** — `discord-bot/src/modules/economy/types/{economyConfig,wallet,shopItem}.ts`. `EconomyConfigSchema`: `enabled`, `currencyName` (default "Crédits ETHONE"), `currencySymbol` (default "🪙"), `dailyAmountMin`/`dailyAmountMax`, `dailyCooldownHours` (24), `startingBalance` (0), `gambleMinBet`/`gambleMaxBet`, `gambleWinMultiplier` (~1.9), `transfersEnabled`. `WalletSchema`: `userId`, `guildId`, `balance`, `lastDailyClaimAt`, `totalEarned`, `totalSpent`, `username`, `avatarUrl` (denormalized, same as `UserXpData`). `ShopItemSchema`: `id`, `roleId`, `label`, `price`, `description`, `enabled`.
- **Storage** — `economy/storage/economyStorage.ts`, modeled on `levelingStorage.ts`'s **synchronous** `fs.writeFileSync`-per-mutation pattern, NOT the write-buffer pattern (`xpWriteBuffer.ts`). Reasoning: balance mutations are discrete, cooldown-gated, user-initiated commands (low frequency), and losing a real balance change on crash is a worse user-facing problem than the throughput cost of a sync write. Files: `data/economy_wallets.json`, `data/economy_configs.json`, `data/economy_shop.json`. Give `/daily` its own persisted `lastDailyClaimAt` (must survive restarts), unlike leveling's in-memory message cooldown.
- **Race-condition guard**: in `/pay` and the gamble command, do the balance read-check-mutate-write as one synchronous block with no `await` in between, and only `await interaction.reply(...)` after the write completes — prevents a double-spend from a rapid-fire double-click.
- **Service** — `economy/services/economyService.ts`: balance ops, daily-claim logic, transfer, gamble RNG (server-side clamp of bet to config min/max AND to current balance — never trust client input), shop purchase (checks bot role-hierarchy position before `member.roles.add()`, inline, same as every other module — there's no centralized helper).
- **Commands** — single `discord-bot/src/modules/economy/commands/economyCommand.ts` with subcommands `balance`, `daily`, `pay`, `leaderboard`, `gamble`, `shop`/`buy` (bundled like `/antiraid`, not 6 top-level commands). Give `/pay` its own small fixed cooldown (~5s) independent of the admin-configurable `commandCooldown`, to block transfer-spam griefing.
- **Routes** — new `discord-bot/src/server/routes/economyRoutes.ts` (overview, wallet, leaderboard, config GET/PATCH with `emitConfigUpdated('economy', ...)`, shop CRUD).
- **3 registration touchpoints**: import + register command in `discord-bot/src/handlers/commandHandler.ts`; mount router in `discord-bot/src/server/index.ts` (`/api/guilds/:guildId/economy`); **skip** `messageCreate.ts` wiring — no passive per-message earning in v1, note it as the natural future extension point if asked later.
- **Dashboard page** — new `ethone-next/app/discord/economy/{page.tsx,EconomyCenterClient.tsx}`. Clone the real live-fetch pattern from `ethone-next/app/discord/forms/FormsCenterClient.tsx` (`BOT_API_URL`, `guildParam`, `isDemo` fallback) — explicitly **do not** clone `LevelingCenterClient.tsx`, which is a pre-existing, fully-mock page (857 lines, zero fetch calls) unrelated to this task; leave it as a separately-flaggable bug.

## 3. Habit/goal tracker — new dashboard module

Lives at `ethone-next/app/habits/` (sibling to `app/tasks/`, not under `/discord/` — it's a personal productivity feature, not guild-scoped).

- **Migration** — new `supabase/migrations/202609180001_ethone_habits.sql`, modeled directly on the `tasks` table migration (`supabase/migrations/202608290001_cloud_sync_foundation.sql` L77-116: same RLS shape — `enable/force row level security`, owner-scoped policies on `user_id = (select auth.uid())`, `revoke ... from anon` / `grant ... to authenticated`).
  - `habits`: `id uuid pk`, `user_id uuid references auth.users`, `name text not null`, `description text`, `icon text`, `color text`, `target_per_week int default 7`, `is_archived boolean default false`, `created_at`, `updated_at`.
  - `habit_completions`: `id uuid pk`, `habit_id uuid references habits on delete cascade`, `user_id uuid references auth.users`, `completed_on date not null`, `created_at`, `unique (habit_id, completed_on)`. 3 policies (select/insert/delete — "toggle a day" is delete-if-exists/insert-if-not, no update needed), plus an index on `(habit_id, completed_on desc)` for streak queries.
- **Hook** — new `ethone-next/lib/hooks/useHabits.ts`, cloning `useTasks.ts`'s structure (session tracking, realtime subscription on `habits` via `postgres_changes` filtered to `user_id`; skip realtime on `habit_completions` for v1 to cap scope). Adds one method `useTasks.ts` doesn't have: `toggleToday(habitId)` (delete-or-insert a `habit_completions` row for today, optimistic update), plus derived `getStreak(habitId)` / `getHistory(habitId, days)` from the loaded completions.
- **Page** — list of habits with today's toggle + streak count + a history strip. Reuse the already-exported `startOfWeek`/`addDays`/`dateKey` from `ethone-next/components/ActivityHeatmap.tsx` for the history grid — do not reimplement date math.
- **"Today" is computed client-side** (browser-local date), matching how the rest of the tasks/habit UI already treats dates — no timezone-aware pattern exists elsewhere to mirror instead.
- **5 registration edits** (same pattern as the sidebar-hide feature added earlier this session): `ethone-next/components/Sidebar.tsx` (`APPS` array), `ethone-next/lib/navigation.ts`, `ethone-next/components/FloatingLiquidDock.tsx` (mobile icon map), `ethone-next/lib/settings.ts` (`sidebarItems` default array), `ethone-next/lib/i18n.ts` (a `"habits"` nav-label key in all 5 locale blocks: fr/en/es/de/ja).

## 4. Bot Control Center redesign

`ethone-next/app/discord/bot/BotControlClient.tsx` (~3044 lines) uses zero shared UI primitives (hand-rolled Tailwind throughout) and has 15 flat tabs. Do the 5 independent data-wiring fixes first (each self-contained, low-risk) before touching layout/visuals, so value ships even if the visual pass gets time-boxed.

### Data-wiring fixes, in effort order
1. **Commands tab** (trivial) — the real fetched `commands` state already exists but the JSX renders a hardcoded 33-entry static array instead. Swap the render target.
2. **AI & Tokens tab** — `GET /api/bot/ai` already works server-side (`botControlRoutes.ts` ~L163, `BotAiMonitorService.getAiStats()`). Add the fetch, replace the static numbers.
3. **Security & Audit tab** — same shape: `GET /api/bot/security` already works (`BotSecurityAuditService.getSecurityAudit(client)`, ~L193). Replace the hardcoded "98/100" score and mock role arrays.
4. **Configuration tab** — `discord-bot/src/server/routes/settingsRoutes.ts`'s `PatchSettingsSchema` currently omits `botPersonality`, `commandCooldown`, and `themePreset` even though `GuildConfigSchema`/`guildConfigService` already support them (confirmed by grep — zero matches). Since `z.object()` silently strips unrecognized keys, sending these today is a no-op, not an error. Add the 3 fields to the schema first, then wire the corresponding form fields in the Configuration tab to the existing PATCH — no new `emitConfigUpdated` call needed, `guildConfigService.updateConfig()` already emits internally (centralized earlier this session).
5. **Performance & RAM tab** — the only item requiring new backend work. `botControlRoutes.ts`'s `GET /api/bot/performance` (~L132-160) currently generates sine-wave random numbers with no real data source, and `BotTelemetryService` (`discord-bot/src/modules/botControl/services/botTelemetryService.ts`) has the *shape* of real tracking (`pingHistory`, `recordPing()`, `eventCounter`/`commandCounter`) but is seeded with hardcoded fake starter values (`[18, 22, 19, 25, ...]`, `currentEventsPerMin = 142`) and needs verifying whether `recordPing`/`incrementEventCount` are actually called anywhere live. Fix: confirm/wire real callers for those methods, add a `setInterval` sampler (~30s) pushing `{ timestamp, pingMs, heapUsedMb: process.memoryUsage().heapUsed/1024/1024, cpuPercent, eventLoopLagMs }` into a bounded ring buffer (e.g. 2880 entries = 24h at 30s), and change `/performance` to slice real buffered points by the requested `window` instead of generating fake ones. Judgment call to flag in the response, not block on: p95/p99 latency computed from one ping sample per 30s bucket isn't a meaningful percentile — consider shipping raw ping-over-time instead of fabricated percentiles for this metric specifically.

### Layout/visual pass (time-boxed, after the 5 fixes above)
Regroup the 15 tabs into 5 top-level groups: **Overview** (Vue Générale, Présence & Activité), **Configuration** (Configuration, AI & Tokens, Modules Actifs), **Health & Performance** (Performance & RAM, Diagnostics, Sous-Systèmes, Serveurs Installés), **Security** (Sécurité & Audit, Incidents & Erreurs — stays inside Bot Control per user confirmation), **Operations** (Intégrations, Tâches Planifiées, Commandes, Flux d'Événements). Split `BotControlClient.tsx` into one file per group as part of this pass (makes the primitive migration tractable incrementally instead of one giant diff). Migrate outer chrome onto `ethone-next/components/ui/{Tabs,Card,Badge,StatusIndicator}.tsx` (confirmed present) — tab bar → `Tabs`, card containers → `Card`, status pills → `Badge`/`StatusIndicator`. Cap this pass at outer-chrome migration; don't attempt to rewrite every tab's internals in one sitting.
